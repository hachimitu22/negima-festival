# テスト設計

この分類は、ゲームの仕様と詳細設計をどのように検証するかを定める。
現在は単体テストケースだけを対象とし、テストコードと統合テストケースは扱わない。

## 単体テスト方針

書籍『単体テストの考え方/使い方』で示されている次の性質を満たすテストを単体テストとする。

- 単体と呼ばれる少量のコードを検証する。
- 実行時間が短い。
- 他のテストから隔離された状態で実行する。

このプロジェクトでは古典学派の考え方に沿って、次の規則を適用する。

- 1ケースでは、公開APIから観察できる1つの振る舞いを検証する。
- 小さなインメモリの協力オブジェクトは実物を使用する。
- ライブラリ製、手製を問わずモックを使用しない。
- ケースごとに新しい入力値とインスタンスを生成する。
- テストの実行順、他のテストが残した状態、共有可変状態へ依存しない。
- 外部I/O、実時間の待機、乱数、DOM、ゲームループへ依存させない。
- privateなフィールドやメソッドではなく、公開された結果と状態を検証する。

単体は必ずしも1クラスとは限らない。
外部I/Oや共有状態を持たない少数のドメインオブジェクトが協調して実現する振る舞いも、1つの単体として検証できる。

## Test SuiteとTest Case

Test Suiteは関連する公開上の振る舞いを分類する親単位とする。
Test Caseは独立した入力条件または状態遷移を検証する子単位とする。

- suite IDは`PT-UT-S01`の形式とする。
- case IDは親suiteのIDにcase番号を加えた`PT-UT-S01-C01`の形式とする。
- 将来のテストコードではsuite IDと名称を`describe`または`suite`へ、case IDと名称を`test`または`it`へ対応させる。
- suiteは分類だけに使用し、case間でfixture、インスタンス、状態を共有しない。
- 一度割り当てたIDはテストコード作成後に変更しない。

各caseは次の共通フォーマットで記載する。

- 前提
- 入力
- 操作
- 期待結果

異なる入力パターン、境界値、事前状態は個別caseとする。
任意順の訪問や進行前後の比較など、連続操作全体で1つの振る舞いを検証する場合は分割しない。
table-drivenな実装を使用する場合も、各caseを個別のtestとして登録し、case ID単位で結果を報告する。

## テストコードの構成

単体テストコードはAAA形式で記述する。
各caseでフェーズの開始位置へ次のコメントを記述し、準備、操作、検証を明確に分離する。

```js
// Arrange

// Act

// Assert
```

例外を検証するcaseでは、Arrangeで入力を準備し、Actで実行対象の関数を作り、Assertでその関数の実行結果を検証する。

## 統合テスト

現時点では統合テストケースとテストコードを作成しない。
`MainGameScene`と`PatrolEventManager`の接続、renderer表示は将来の統合テスト対象とする。
