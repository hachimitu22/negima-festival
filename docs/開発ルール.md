# 開発ルール

この文書は、設計から実装までの共通作業順と実装前ゲートを定める。
人間とエージェントのどちらが作業する場合も、この文書を正本とする。

## 標準作業順

コード実装を伴う作業は、必ず次の順で進める。

1. 基本設計
2. 詳細設計
3. 必要ならテストケース
4. コード実装

プレイヤーから見た挙動、ゲームルール、状態遷移を変更する場合は、先に`docs/基本設計`へ意図した挙動を記述する。
責務、公開API、データフロー、依存方向を変更する場合は、コード実装前に`docs/詳細設計`へ実装上の設計を記述する。

## 実装前ゲート

コード実装に入る前に、次の項目を確認する。

- 関連する基本設計が、今回実装するプレイヤー向け挙動を説明している。
- 関連する詳細設計が、今回変更する責務、公開API、データフロー、依存方向を説明している。
- 公開APIから観察できる振る舞いを追加または変更する場合は、対応するテストケースが`docs/テスト設計`にある。
- 仕様と実装の差分が変わる場合は、`docs/実装状況.md`の更新内容が明確になっている。
- DOM viewを変更する場合も、ゲームルール、イベント発生タイミング、layer状態、ループ挙動をDOM側へ移さない方針を満たしている。

関連する設計文書が存在しない、または文書同士が矛盾している場合は、原則として先に文書を整える。
その時点で実装しない差分や未確定事項は、対象文書の未決事項または`docs/実装状況.md`へ記録する。

## テストケース更新の判断

次の場合は、コード実装前に単体テストケースを追加または更新する。

- 新しい公開APIを追加する。
- 既存の公開APIから観察できる結果、状態、例外、状態遷移を変更する。
- 既存の仕様に対して、未検証の境界値、入力パターン、事前状態を実装する。

privateな実装だけを整理し、公開APIから観察できる振る舞いが変わらない場合は、新しいテストケースを必須としない。
ただし、既存テストケースの意図と実装内容が食い違う場合は、テスト設計を更新する。

## コード実装時の制約

- 仕様の正本は基本設計、実装上の契約の正本は詳細設計とする。
- 実装中に設計と異なる判断が必要になった場合は、先に設計文書を更新する。
- 実装状況だけを根拠にゲーム仕様を決めない。
- DOM viewは暫定rendererとして扱い、DOM UIの完成自体を主目的にしない。
- 明示的な依頼がない限り、VueやReactなどのDOMフレームワークを導入しない。

## 検証

文書を追加または変更した場合は、原則として`npm run docs:build`でVitePressのリンクとビルドを確認する。
コード実装を伴う場合は、変更範囲に応じて該当するテストまたは静的チェックを実行する。
